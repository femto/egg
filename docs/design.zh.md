# Egg 语言设计

Bingnan Zheng · 2026-10-22

[English](design.md) · 中文

## 概述与设计理念

Egg 是一门 AI 原生的系统编程语言：核心不带任何能力，异常、IO、分配都是用户按需声明的能力模块。名字取自“一切从蛋里孵化出来”。

三条核心原则：

1. **核心什么能力都没有**：没有 GC、没有异常、没有隐藏的分配、没有 IO、不依赖操作系统。
2. **能力显式声明，编译器递归检查**：模块声明它需要的能力，编译器沿调用图确认没有越界。
3. **为 AI 而设计**：核心小到能完整放进上下文，每个能力都附带机器可读的规范、示例和测试。

这个设计带来一个结构性的好处：**运行时就是受限子集**。Go 的运行时要靠 `nosplit`、`nowritebarrier` 这类特殊规则来约束，Egg 不需要。异常机制是用“不声明任何能力”的核心代码写成的能力库，编译器则是一个声明了 `alloc`、`io` 的普通程序。最底层的代码天然受限，而且由编译器检查。

第二个好处是**核心天然跨平台**：所有与操作系统有关的代码都被限制在能力模块里。

## 核心语言

核心以 Zig 为参照但更小：只保留不需要运行时支持的特性。函数签名必须写类型，函数内部可以推断，以避免全程序类型推断带来的编译慢、难以增量编译的问题。

| 类别 | 内容 | 首次出现 |
| --- | --- | --- |
| 整数 | `i8`…`i64`、`u8`…`u64`、`usize` | v0（先只做 `i64`）；v2 加齐所有宽度 |
| 其他基本类型 | `bool`、`f32`、`f64`、`void` | v0 |
| 复合类型 | `struct`、`enum`、标签联合 | v1 |
| 指针与内存 | 切片、数组；单项指针 | v1；裸指针在 v2（持有指针是安全的；`p.*` 等指针操作需要 `allow unsafe`） |
| 控制流 | `if`、`while`、`for`、`switch`，全部是表达式 | v0（先做 `if`、`while`） |
| 错误 | 错误作为值（类似 `!T`）、`try` | v1 |
| 编译期 | `comptime` 参数、泛型（返回 `type` 的函数）；反射（`@typeInfo`） | v1；反射在 v1 之后 |

**类型语法采用前缀写法，从左往右读**（同 Go、Zig）：`[4]u8` 是 4 字节数组，`[3][4]u8` 是 3 行 4 列（访问顺序 `grid[2][3]` 与类型一致），`[]u8` 是切片，`*[4]u8` 是指向数组的指针，`?T` 是 `T` 或 `null`（`*T` 本身就可以为空，所以不用 `?*T`），`!T` 是可能出错的值。不采用 Rust 的 `[u8; 4]`：它是唯一把元素类型夹在中间的写法，嵌套时要从里往外读。

刻意不进入核心的特性：

- 运算符重载、隐式类型转换：对人略烦，对 AI 和审阅者更清楚
- 闭包：需要捕获环境，通常意味着分配，属于能力范畴
- 异常、堆分配、IO：全部作为能力模块提供
- 垃圾回收：语言里完全没有。堆内存只靠所有权管理（唯一所有者，沿每条路径检查）：释放是显式的，运行时既没有回收器，也没有所有权检查。v3 之前，字符串和 `a.create` 仍放在程序级 arena 里

错误作为值放进核心，是因为它只是“返回值加一个标签”，不需要任何运行时支持；异常需要栈展开，所以不进核心。

v0 语法示例（暂定）：

```
fn fib(n: i64) i64 {
    if (n < 2) { return n }
    return fib(n - 1) + fib(n - 2)
}

fn main() i64 {
    return fib(20)
}
```

## 能力系统

模块（一个文件）在头部用 `uses` 声明能力，编译器推断每个函数实际用到的能力，并沿调用图递归检查。能力要通过一个值（`Io`、`Allocator`）来使用：这个值只有 `main` 能从运行时拿到，再显式往下传。拿不到这个值的代码碰不到能力；所在模块没有声明的代码，拿到了值也不能用。没有声明任何能力的模块就是纯核心代码。

只用核心，不声明能力：

```
fn hash(bytes: []const u8) u64 {
    var h: u64 = 0xcbf29ce484222325
    for (bytes) |b| { h = (h ^ b) * 0x100000001b3 }
    return h
}
```

声明需要的能力（文件读写之后才加；缓冲区、`free` 和 `defer` 在 v2 已有）：

```
uses alloc, io

fn read_config(io: Io, a: Allocator, path: str) !Config {
    const text = try io.read_file(a, path)   // 调用者拥有的 Buf(u8)
    defer a.free(text)
    return parse(text[0..])
}
```

第一批能力：

| 能力 | 提供什么 | 计划版本 |
| --- | --- | --- |
| `alloc` | 堆分配，分配器显式传递 | v2（字符串放在程序级 arena；可释放的独占缓冲区 `Buf(T)`，带所有权检查） |
| `io` | 文件、标准输入输出，按操作系统各有实现 | v2（先做标准输出，文件之后再加） |
| `raise` | 异常抛出与捕获，用核心代码实现 | v3 之后 |

检查规则：

1. 模块内的函数不能使用模块头部没有声明的能力（E130）。
2. 编译器沿调用图推断每个函数的能力集合，包括间接调用、跨模块调用和泛型实例：没有 `uses io` 的模块，即使在用 `Io` 实例化的泛型函数里也不能打印。
3. 签名上不写能力集合，由工具展示（语言服务器的悬停提示会显示）。

## AI 原生特性

Egg 假设 AI 在上下文里现学这门语言，而不是依赖训练数据：一门用户可扩展的新语言几乎没有训练数据，所以规范本身必须能被 AI 直接读懂。

- **机器可读的语言规范**：放在仓库的 `spec/` 目录，核心语言的完整定义控制在能一次放进上下文的规模。
- **每个能力模块必须附带三样东西**：规范说明、示例代码、测试。没有这三样的能力不能发布。
- **结构化诊断**：编译器可以输出 JSON 格式的错误，包括位置、违反的规则编号、可能的修复方式，AI 可以据此自动修正。
- **唯一的标准格式**：内置格式化工具，没有任何配置项，AI 生成的代码天然风格一致。
- **语法规整、没有歧义**：每种结构只有一种写法，没有运算符重载和隐式转换。
- **能力检查是安全网**：AI 生成的代码可能出错，但编译器保证它不会使用没有声明的能力。

代码比 Rust 长一些是可以接受的代价：大部分代码由 AI 生成时，显式反而方便 AI 和审阅者判断代码在做什么。

## 编译器架构

第一个编译器 `eggc` 用 Spinel 能编译的 Ruby 子集编写：开发时用 CRuby 直接运行，发布时用 Spinel 编译成原生二进制。输出是 C 代码，交给系统 C 编译器。

编译流水线：

1. 词法分析（`lexer.rb`）
2. 递归下降解析，生成 AST（`parser.rb`）
3. 加载导入的模块，合并成一个程序，v2 加入（`loader.rb`）
4. 类型检查（`typecheck.rb`）
5. 能力检查，v2 加入（`caps.rb`）
6. 缓冲区所有权检查，v2 加入（`own.rb`）
7. 生成 C 代码（`codegen_c.rb`）
8. 调用 C 编译器得到可执行文件

项目结构：

```
egg/
├── bin/eggc
├── lib/egg/
│   ├── lexer.rb
│   ├── ast.rb
│   ├── parser.rb
│   ├── loader.rb
│   ├── typecheck.rb
│   ├── caps.rb
│   ├── own.rb
│   └── codegen_c.rb
├── spec/          # 机器可读的语言规范
├── examples/
└── test/
```

编码约定（为了留在 Spinel 子集内）：

- 不使用 `send`、`define_method`、`method_missing`、`eval`。
- AST 节点用 `Struct` 定义，处理节点一律用 `case … in` 模式匹配，不用 visitor 双重分派。
- 每个 `case … in` 最后加一个 `else` 分支，抛出带节点类型的清晰错误，因为 Ruby 不检查分支是否完备。
- 不依赖任何 gem，解析器手写。
- 尽早写一个小例子，验证 Spinel 对“多种节点类型混在一个数组里”的类型推断效果；效果不好就改用“单一 `Node` 类加 `kind` 字段”。

这些约定也为以后用 Egg 重写编译器做准备：`case … in` 可以几乎一对一地翻译成 Egg 的 `switch` 处理标签联合。

## 自举与跨平台

自举链上没有任何需要信任的预编译二进制，只从 C 编译器出发。用户则只需要一个 C 编译器，不需要安装 Ruby。

自举链：

1. C 编译器构建 CRuby。
2. CRuby 直接运行 `eggc` 的 Ruby 源码，编译 Egg 程序为 C。
3. 可选：Spinel 把 `eggc` 编译成原生二进制，用于提速。
4. v4 起：用 Egg 重写 `eggc`，由上一代编译器编译，完成自举。
5. 验证：第二代和第三代编译器的输出应逐字节一致。

分发方式参照 Nim 和 Zig：发布 `eggc` 生成好的 C 代码，用户用任意 C 编译器（MSVC、clang、MinGW）编译即可。

Windows 策略：

- CRuby 和 Spinel 只是开发者的工具，Windows 用户不需要它们。
- 可以用 `zig cc -target x86_64-windows-gnu` 在 Linux 上直接交叉编译出 Windows 版本。
- Windows 上的开发者可以使用 WSL。
- Spinel 已经支持原生 Windows 构建（MinGW-w64 + UCRT，见仓库里的 win32.mk），用 Spinel 编译出的 eggc 可以直接发布 Windows 版。

Egg 自己生成的 C 代码必须从第一天起保持可移植：

- 只用标准 C（C99 或 C11），核心部分不调用任何 POSIX API。
- 平台相关的代码全部放在能力模块里，例如 `cap.io` 为 Linux、macOS、Windows 各提供一份实现，通过 comptime 按编译目标选择。

## 路线图

每个阶段以一个可以自动验证的结果作为关口。v3 补全不靠 GC 的内存管理，`raise` 是对“运行时即受限子集”这一设计的第一次检验，v4 是自举目标。v0、v1、v2 已完成；完整的反射（`@typeInfo`）推迟到 v1 之后。v2 的第一步能力检查（模块、`uses`、`Io` 与 `Allocator` 能力值、E130）已完成。第二步也已完成：全部宽度的整数类型和 `@as`；裸指针，只能在声明了 `allow unsafe` 的文件里使用（只对本文件有效，不沿调用图传递，所以 unsafe 模块可以对外提供安全的 API）；函数值；以及在声明里写明所用能力的 `extern fn`。函数值最后不需要 `allow unsafe`：能力检查把"把函数当值取出"算作一次调用，所以函数值和 `Io` 值一样携带能力。第三步加入所有权：`Buf(T)` 是只有一个所有者的堆缓冲区，由 `a.alloc` 创建、`a.free` 释放。检查是线性的：沿每条路径，缓冲区只能在拥有时使用，所有者离开作用域之前必须释放、返回或传走，所以不会有释放后使用、重复释放和泄漏。它不需要生命周期标注，因为切片本来就是二等公民：借出的切片活不过那次调用。缓冲区最初只能放在局部变量、参数和返回值里；后来含缓冲区的结构体、数组和缓冲区本身也成为被拥有的值。结构体变量的字段逐个追踪，所以可以释放并换掉 `v.data` 而 `v` 仍可使用，`inout self` 方法也能就地扩容自己的缓冲区。容器的元素不追踪：只能就地借用，用 `@replace`/`@take` 换出；`Buf(T).empty` 是不占内存的空缓冲区，`a.free` 会释放一个值持有的全部内存。`defer` 和 `errdefer` 随之加入，否则在每条错误路径上释放几乎写不出来。字符串和 `a.create` 仍放在程序级 arena 里。v3 原计划做 GC，2026-10-27 决定不做：真实一点的程序（会扩容的哈希表、就地改写的树）在所有权规则下都写得出来，所以 v3 改为补上它们暴露的两个缺口：只读方法也得写成 `inout self`，字符串永不释放。第一个缺口已经补上：参数默认借用，接管所有权的参数用 `sink` 标出。

| 阶段 | 内容 | 验收关口 |
| --- | --- | --- |
| v0 · 核心子集 ✅ | `i64`、函数、`if`、`while`、`return`；生成 C，交给系统 C 编译器 | `fib.egg` 编译运行，输出 6765 |
| v1 · 类型与 comptime ✅ | 带方法的 `struct`、`enum`、标签联合、`str`、数组、二等切片、`inout`；错误值；comptime 泛型；`@sizeOf`、`@typeName` | 泛型 `Pair` 与错误值示例通过测试 |
| v2 · 能力检查 ✅ | 模块；实现 `alloc` 与 `io` 两种能力；编译器沿调用图递归检查；整数类型、裸指针、函数值、`extern fn`；缓冲区所有权、`defer` | 越界使用能力的程序被拒绝 |
| v3 · 不靠 GC 的内存管理 | 只读借用参数；像缓冲区一样释放的 owned 字符串 | 反复拼字符串的长时间循环内存保持不变；泛型 map 的只读方法用借用而不是 `inout self` |
| v4 · 自举 | 用 Egg 重写 `eggc`，由上一代编译器编译自己 | 第二代与第三代输出逐字节一致 |

## 待决问题

- [ ] 语句结尾是否需要分号？示例暂时省略分号，需要和解析器的简单性一起权衡。
- [x] 能力写在签名上的语法：`fn f() !void with io`，还是只在模块头部声明、由工具生成文档？v2 已定：模块级 `uses alloc, io`，能力值显式传递；签名上不写能力列表，由工具展示每个函数的能力集合。
- [ ] 能力的粒度：`io` 是一个能力，还是拆成 `fs`、`net`、`stdio`？v2 先只做一个 `io`（只有标准输出），加入文件时再重新考虑。
- [x] 释放内存后如何保证安全？v2 已定：独占的 `Buf(T)`，线性检查（只移动、不复制；每条路径上恰好释放或传走一次），配合 `defer`/`errdefer`；释放从不隐式发生。字符串仍放在永不释放的 arena 里。
- [x] 要不要 GC？2026-10-27 已定：不要，内存只靠所有权管理。
- [ ] 拼出来的字符串怎么释放：像 `Buf(T)` 一样检查的 owned 字符串类型、`str` 只留给字面量和借用，还是别的办法？属于 v3。
- [x] 只读借用参数怎么写，`self` 是否默认用它？v3 已定：参照 Hylo，普通参数（包括 `self`）借用 owned 值，`sink x: T` 接管它，调用处都写 `f(x)`。
- [x] 位运算的优先级怎么定，`<<` 丢位时要不要 panic？2026-10-29 已定：参照 Zig，`& | ^` 比比较运算结合得紧，`<< >>` 介于它们和 `+ -` 之间，但 `& | ^` 不加括号不能混用（E002）；`<<` 丢掉移出的位，移位位数小于 0 或不小于位宽时 panic；操作数可以是任意整数类型（有符号按补码算，`>>` 补符号位），移位位数也可以是任意整数类型；同时加了 `0x`、`0b` 字面量。
- [ ] 异常机制采用 `setjmp`/`longjmp` 还是“每次调用后检查”？
- [ ] comptime 在 Spinel 写的编译器里如何执行：解释 AST，还是生成 C 再运行？
- [ ] 能力是否允许用户自定义，还是第一版只提供内置的几种？
